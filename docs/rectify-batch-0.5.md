## 一、做了什么

### 1. 自动检查进仓库、进 CI

`scripts/prompt_audit.py` 原本就有（查路由表工具、路径、手册索引、目录 token），我加了第 5 项：**祈使句基线**。

- 基线文件 `scripts/prompt_imperative_baseline.json`，首次运行自动写
- 接入 `.github/workflows/build-ios-ipa.yml` 的「Check standalone sources statically」步骤，跟括号配平一起跑
- 超基线直接 FAIL，并指出是哪个文件多了几处

**为什么这样做**：整改包要的不是"这次改整齐"，是"以后也整齐"。人记不住，机器记得住。

### 2. 例外表建起来了

`docs/prompt-text-inventory.md` 里 11 条（E1–E11），每条写清位置、为什么不能撤、什么时候能撤。

**为什么要有例外表**：基线只降不升，如果不给"必须留着"的句子一个合法去处，下一个人只会为了过检查而删掉该留的话——那比不检查更糟。

### 3. 牵连清单建起来了

`docs/prompt-impact-map.md`，7 条提示词构建路径（P1–P7）、4 条非聊天链路（N1–N4）、4 条 user-role reminder（R1–R4）、5 条其他（O1–O5）。

**为什么要这张表**：同一个模型看的是好几条路径拼出来的话。改主流程不改压缩，长对话一压缩人设就换了——这就是"信息断层"。

## 二、核出来的两个真问题

### 问题 1：批 0 的基线数字是假的

批 0 记「严格祈使句 19 处」。补上多行字符串扫描、补齐中文词表、剔掉 Swift 代码误报后，真实数字是 **34 处**（另 12 处技能手册正文单独统计）。

原因：批 0 的扫描只认单行字符串字面量（`"..."`），而提示词正文大多是 `"""` 多行块。压缩引擎、贴纸目录、技能正文，全都没被扫到。

**这不是小事**：拿一个漏扫的数字当验收基线，等于闭着眼睛验收。

### 问题 2：两处提示词有第二来源，批 2 漏了

| 位置 | 问题 | 影响 |
|---|---|---|
| `+Compaction.swift:1230` | 压缩提示词里称模型为 `The agent will read your summary` / `the agent needs` | 长对话一压缩，模型读到自己被叫 "agent"，人设被往前推 |
| `AIChatView.swift` `StickerStore.systemPromptFragment()` | 中文，带「核心原则」「规则：1. 2. 3.」规章腔 | 每轮都在，模型读到的是执行者手册 |

两处都还没改，只登记了。
